## Blockers

### B1 — The design's central premise is false: the ladder is already live
`[both]` `[gap]` — **verified**

The design asserts (§1) that "the recidivism ladder is not running on cds1 at 7
days. It is not running at all, because the code has never been deployed."

That is wrong. The temp→perm ladder shipped in **v1.0.0** and is present in every
tag since:

```
$ git show v2.10.0:lib/score.sh | grep -n 'prior + 1'
500:            if (( prior + 1 >= REPEAT_N )); then action="perm"
$ git show v2.10.0:lib/common.sh | grep -n 'REPEAT_N=\|REPEAT_WINDOW_DAYS='
94:REPEAT_N=3
95:REPEAT_WINDOW_DAYS=7
```

cds1 has run `SWATTER_MODE=enforce` since 2026-06-12, and this project's own
earlier design work **measured the ladder running on cds1 at 5.37 escalation
events/day, spiking to 16** (`2026-07-24-recidivism-escalation-design.md:501`).

The handoff's "nothing was deployed" refers to the unreleased *improvements* —
preview, rollback, tripwire, unblock watermark, CRITICAL-single bar, `rule=`
stamping — not to the ladder itself. The design misread it.

**Consequences, all of which invert the plan's risk direction:**

| Design assumption | Reality |
|---|---|
| The deploy is when temps start becoming perms | They have been becoming perms since v1.0.0 |
| Gate B is "boring — no behavior change" | Deploying changes ban arithmetic, in the **safer** direction |
| Delaying the deploy is the cautious choice | Delaying **keeps cds1 on the less-safe ladder** |
| `REPEAT_ENABLE=false` at gate B is a no-op | It **disarms a live ladder** — a real policy change |

Every unreleased change reduces false perms: the unblock watermark stops an
operator's correction being silently undone; the CRITICAL-single bar raises 3→4
for cheap single probes; the residue fix stops report-mode ghosts perm-banning on
sight; the tripwire alerts on a runaway wave. **Shipping sooner is the safer
move, not the riskier one.**

**Required before any install:** capture cds1's actual state — installed version,
enforced perm count, and a sample of perm reasons — rather than inferring it.

### B2 — The kill switch does not stop queued permanent bans
`[both]` `[gap]` — **verified**

§7 claims `REPEAT_ENABLE=false` is "instant; stops new ladder perms." It is not.

`_swatter_retry_pending` runs **first** in every scan (`lib/score.sh:478-482`)
and replays a stored intent through `_swatter_apply_plane` (`:434-435`) with no
re-consultation of the ladder, the threshold, or the switch. A ladder perm whose
backend call failed while armed sits in `pending_blocks` and lands on a later
scan — up to `PENDING_RETRY_MAX_ATTEMPTS=12` attempts or
`PENDING_RETRY_MAX_AGE_HOURS=24` (`lib/common.sh:122-123`) **after** the operator
believes they have disarmed.

**Required:** either the switch refuses queued `perm` intents whose reason
contains `recidivism=`, or the abort procedure explicitly drains those
`pending_blocks` rows. Tests must cover "disarmed + queued perm intent."

### B3 — Gate D drops the preview that the whole handoff exists to enforce
`[pass-a]` — **verified**

The handoff's Phase 4 requires `escalate-preview --window 30`, human review, then
the flip. The design's gate C previews at **7** and gate D flips to 30 with **no
preview at 30 and no second review**.

A clean list at 7 days says nothing about who appears when the window triples.
This reopens precisely the "clean list, then ban the cohort that wasn't on it"
failure mode that the pre-2026-07-24 `escalate-preview` off-by-one already cost
this project once.

**Required:** gate D = preview@30 → review → allowlist → flip, with the same
discipline as gate C.

### B4 — AbuseIPDB is never frozen, though the design names it as irretractable
`[pass-b]` `[gap]` — **verified**

§7 correctly lists two things rollback cannot undo: the swarm hub and AbuseIPDB.
Gate C freezes only `SWARM_PUBLISH`. There is no step for `ABUSEIPDB_REPORT`.

Reporting fires on a successful primary block (`lib/score.sh:208-210`) and
`ABUSEIPDB_REPORT_MIN_ACTION` defaults to `perm` (`lib/common.sh:85`) — so ladder
perms are exactly what gets published. `rollback-ladder` only prints a warning
about it (`bin/swatter:599-606`); there is no retract API.

The global default is `false` (`lib/common.sh:79`), but a default is not a
control. **Required:** verify its live state on cds1 and hold it off for the
same window as the swarm freeze.

### B5 — The deploy is not atomic against the live `*/5` cron
`[pass-b]` `[gap]` — **verified**

`install/install.sh` copies libs, then the binary, then cron, with no `flock`, no
cron pause, and no atomic directory swap. A scan starting mid-copy can source a
mixed tree. The design's gate B never mentions a maintenance hold.

**Required:** an explicit ritual — pause `/etc/cron.d/swatter`, install,
`test-config`, one manual scan, re-enable.

Good news verified in passing: the installer **preserves** an existing
`/etc/swatter/swatter.conf` (`install/install.sh:225-227`), so a pre-set switch
is not clobbered.

## Majors

### M1 — Default-off silently disarms a live ladder on every upgrade
`[pass-a]` — **accepted, and it reverses an earlier decision**

Given B1, `REPEAT_ENABLE` defaulting to false means any install upgrading to
v2.11.0 — cds1 included — **stops** ladder perms it has been placing since
v1.0.0. The installer preserves the conf and will not inject the key, so unset
resolves to `false`.

Default-off remains right for *new* installs. For upgrades it is a silent feature
removal. The design needs an explicit upgrade decision rather than one default
serving both. **This is an open question for the owner, not a call to make
silently** — see the summary.

### M2 — Abort thresholds are calibrated against the wrong baseline
`[pass-a]` — **verified**

§7's "expected ~1–2/day net-new" was the *post-30-day-widen* projection from the
earlier work. The measured 7-day-window reality on cds1 is **5.37/day, spiking to
16**. Using 1–2/day as the mental model during the watch will produce either
false panic or false calm. Re-baseline before arming.

### M3 — `rollback-ladder` cannot see historical ladder perms
`[pass-b]` — **verified**

The selector requires `reason LIKE '%recidivism=%'`
(`lib/store_sqlite.sh:206-209`), and that stamp is added by the *unreleased*
`d689160`. Every ladder perm already placed on cds1 — potentially months of them
at ~5/day — is invisible to the undo tool. The design treats `rollback-ladder` as
the universal undo; it is only the undo for perms placed by the new code.

### M4 — `--since` is strict `>` and easy to mis-set
`[pass-b]` — **verified**

`ts > ${since}` misses a ban at the exact arm second, and an operator who notes
the timestamp *after* arming loses everything in between. Record the arm time
**before** arming, and prefer a slightly earlier value.

### M5 — `rollback-ladder` can fail closed while the operator believes it worked
`[pass-b]` — **verified**

It waits up to 120s for the state lock (`bin/swatter:551`) and dies if it cannot
get it. A long scan plus swarm publish can exceed that. The operator has already
flipped the switch and may reasonably assume recovery is done.

### M6 — `test-config` has no escalation-knob output
`[pass-a]` — **verified**

The design assumes `swatter test-config` can answer "is the ladder armed?" It
currently dumps no escalation knobs at all, so that surface is new work, not a
free check.

## Minors

- **m1** `[pass-a]` Commit count drifts as work lands; not worth pinning in prose.
- **m2** `[gap]` `config/swatter.example.conf` and README both need the new knob
  and an upgrade note; `TODO.md` still describes the old "just widen to 30" Phase
  4 and will contradict this design until updated.
- **m3** `[pass-a]` The handoff's §1 should be explicitly annotated as misread, so
  the two documents do not fight.
- **m4** `[pass-a]` The stale comment at `lib/common.sh:330-331` claims an empty
  `REPEAT_WINDOW_DAYS` yields a fail-safe 0-day window; validation now rewrites it
  to 7 first, which arms.
- **m5** `[pass-a]` `escalate-preview` still does not model
  `REPEAT_N_CRITICAL_SINGLE` (documented over-report), so gate C/D lists will show
  some all-critical IPs as one-away that actually need another temp.
- **m6** `[gap]` Widening to 30 at gate D pulls **pre-deploy** temps (which carry
  no `rule=`) back into the window, so `tot == crit` fails and the CRITICAL-single
  bar goes **inert again for another 30 days** — the safer bar is disabled during
  the riskiest change. Not previously identified by anyone.

## Claude-side sweeps

- **[code-review]** Target is a committed design doc, so the working-diff review
  could not bind; an equivalent inline pass was run over the referenced code
  paths. Findings are folded above (B2, B4, B5, m6).
- **[security-review]** Run despite the target being a design, because it governs
  a security tool's ban logic. Findings: B4 (irretractable outbound publication
  not gated) and B2 (safety control with a bypass) are the security-relevant
  ones.
- **[gap]** Independently enumerated every permanent-ban path and confirmed the
  one-line gate is complete *for ladder conversion only*: honeypot instant-perm
  (`lib/score.sh:538`), hard-intel dual-plane (`:356`), plane-upgrade (`:323`),
  residue backfill (`:333`), and pending retry (`:434`) all remain live with the
  switch off. That is correct by the design's own definition of "off," but it
  means **an operator watching gate B will see permanent bans and must not read
  them as the switch having failed.** Ladder perms are distinguishable by
  `recidivism=` in the reason. The design does not say this anywhere.

## Disposition

Nothing here was declined. B1 invalidates the sequencing the design is built on,
so the document requires a rewrite rather than patching, and M1 raises a question
whose answer is the owner's to give.
