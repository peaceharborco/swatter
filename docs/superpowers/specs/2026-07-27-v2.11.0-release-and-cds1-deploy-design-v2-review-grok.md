**Reviewed:** `2026-07-27-v2.11.0-release-and-cds1-deploy-design-v2.md`
**Date:** 2026-07-27
**Reviewers:** two Grok 4.5 passes in lens mode (`[pass-a]` correctness skeptic,
`[pass-b]` safety red-teamer), plus Claude-side inline code-review,
security-review, and gap sweeps (`[gap]`).
**Verdicts:** both passes returned **EXECUTE-WITH-FIXES** — the strategic frame

## Blockers

### B1 — The drain filter I specified cannot match the rows it must catch
`[pass-a]` — **verified**

§3.2 requires the pending drain to skip rows whose reason contains
`recidivism=`. That stamp is written only by unreleased code
(`lib/score.sh:565`, added by `d689160`). **cds1 runs v2.10.0**, whose ladder
perms carry no such token. So every ladder perm queued *today* fails the filter,
and `_swatter_retry_pending` replays it (`lib/score.sh:434-435`) after the
operator disarms — precisely the bypass §3.2 exists to close.

The same applies to a dual-plane secondary, whose reason is `dual-plane ${reason}`
(`:356-357`) and inherits the primary's lack of a stamp.

**Fix:** when the switch is off, refuse *all* queued `action='perm'` intents and
let the next scan re-decide, rather than filtering on a substring that only
future rows carry.

### B2 — Abort is neither atomic nor tool-backed
`[both]` `[gap]` — **verified**

Five independent gaps, all confirmed in code:

1. **Config is sourced once per process** (`bin/swatter:58`). Flipping the conf
   does nothing to an already-running scan, which keeps placing ladder perms
   until it exits.
2. **The drain iterates a snapshot** (`lib/score.sh:373-386`), so clearing rows
   mid-loop does not stop in-flight applies.
3. **There is no CLI at all.** `bin/swatter` contains *zero* references to
   `pending` — the queue cannot even be inspected, let alone drained. Abort step 2
   is undocumented hand-SQL.
4. **If cron is paused for the incident, the drain never runs**, because the
   drain is a side effect of a scan.
5. **Lock contention:** a drain-scan holds the state lock through
   `swatter_swarm_publish`; `rollback-ladder` waits 120s then dies
   (`bin/swatter:551`), returning an empty undo while the operator believes
   recovery happened.

**Fix:** abort becomes: pause cron → wait for no in-flight scan → flip conf →
forced drain under the lock → rollback → verify the pending count is zero. And
`v2.11.0` needs a `swatter pending` / drain command, since the abort path
currently depends on a tool that does not exist.

### B3 — The maintenance hold is undone by the installer itself
`[pass-b]` — **verified**

Gate B says "pause `/etc/cron.d/swatter`, install, `test-config`, run one manual
scan, re-enable." But `install/install.sh:235` unconditionally writes
`/etc/cron.d/swatter` with the live `*/5` schedule, and does so **before**
`refresh-feeds` and `test-config` run at `:240-243`. Any pause by rename, chmod,
or comment is reverted by the install itself, mid-ritual — reopening the exact
window the hold was invented to close.

**Fix:** `install.sh` gains a `--no-cron` (or post-install enable) path, or the
ritual moves the installed cron file aside *after* install and restores it only
once the manual scan is green.

### B4 — "Provisional band with headroom" manufactures a blind spot
`[pass-a]` — **verified, and it invalidates my own §4.4 remedy**

`PERM_RATE_ALERT_PER_RUN/PER_DAY` are the *same knobs* the tripwire fires on
(`lib/score.sh:605`). Raising them to avoid a false abort does not create a
separate abort threshold — it **raises the alarm floor**. A provisional band with
headroom over the known spike of 16 (say 30–40) means a genuine wave at 20–25/day
produces neither an alert nor an abort. The default of 15 did not have that hole.

**Fix:** separate the *alert* threshold from the *abort* threshold. Keep alerts
tight so they still fire, and define abort as operator judgment against a
measured band — never by silencing the only same-run signal.

### B5 — No runbook exists
`[pass-b]` — **verified**

§3.3 says the "perms still appear while disarmed" warning belongs "in the README
and the runbook." There is no runbook anywhere in the repo. §9 updates only
`TODO.md` and the handoff. At 3am the operator would need to hold in their head:
ladder vs honeypot vs dual-plane vs residue perms; where the re-baselined band
lives; that `--since` must pre-date the change; that partial rollback leaves the
firewall hot; that pre-stamp bans need manual `unblock`; and whether install left
cron armed. That is a design document, not a decision tree.

## Majors

### M1 — §1's central table is too rosy
`[pass-a]` — **verified**

"Every unreleased change reduces false permanent bans" does not survive the diff:

| Change | Actual effect on ban arithmetic |
|---|---|
| Unblock watermark | **Reduces** — the only day-1 reduction |
| CRITICAL-single bar | Reduces *when active*; **inert on day 1** until the window is all post-deploy |
| Residue fix | Planned, **not yet written** |
| Perm-rate tripwire | **None** — notify only |
| `escalate-preview` / `rollback-ladder` | **None** — tools, no automatic effect |
| `top` / metrics fix | **None** — display only |
| Knob validation | Mixed — an empty `REPEAT_WINDOW_DAYS` used to yield a 0-day window (never fires); validation now rewrites it to 7, which **arms**. That edge case *increases* escalation. |

"Ship sooner is safer" remains directionally right — but it rests on the
watermark and the residue fix, not on the tools and display commits the table
credits.

### M2 — The gate-C band cannot serve as the gate-D abort baseline
`[both]` — **verified**

Gate C measures at a 7-day window; gate D triples it, which raises volume *by
construction*. §6 admits this in a caveat, then §7 still aborts on exceeding that
band. A quiet soak yields a tight band that a successful widen blows through
(false abort); a busy soak yields a band a real runaway never reaches (silent
failure). Needs a widen-specific band or a rate-of-change trigger.

### M3 — Downgrade is capability amputation, not an abort path
`[pass-b]` — **verified, and it corrects an earlier claim of mine**

The new index is additive and v2.10.0 tolerates it, so downgrade is *schema*-safe
— which is what I previously reported. But reinstalling v2.10.0 removes
`rollback-ladder`, `escalate-preview`, the unblock watermark, the CRITICAL-single
bar, the tripwire, and `REPEAT_ENABLE` — every recovery tool and safety
improvement at once. It must be documented as **not** the way back.

### M4 — The publication freeze starts at the wrong gate, and leaks elsewhere
`[pass-b]` `[gap]` — **verified**

Perms flow from gate B; the freeze lands at gate D. Through deploy and the ~7-day
soak, ladder perms publish to the swarm hub and AbuseIPDB if live conf has them
on. Separately, the nightly digest mails up to 100 block IPs off-box
(`lib/report.sh:239-249`) regardless of either knob.

**And the freeze is a deferral, not a suppression** `[gap]`:
`swatter_swarm_publish` returns early *before* advancing its cursor
(`lib/swarm.sh:60,66`), so restoring after 14 days publishes the whole backlog at
once. Rolled-back IPs are correctly excluded (the delta requires `o.perm=1`), but
the restore must be a reviewed step, not a blind flip.

### M5 — Monitoring cannot tell you a customer was banned
`[pass-b]` — **verified**

`lib/common.sh:70-72` states it outright: the digest deliberately grades blocks
GREEN, so a runaway "would surface only as a larger number in a mail that still
reads All Clear, up to 24h late." SMS is RED-only. Nothing compares new perms
against the reviewed preview list. The tripwire is therefore the *only* automated
control — which is exactly the one B4 would have blinded.

### M6 — 48h is not proportional to the change
`[pass-b]` At ~5.37 events/day, 48h covers ~10 events and misses weekly traffic
patterns and the multi-day lag typical of "my site is down" tickets.

### M7 — `REPEAT_ENABLE` can desync across read sites
`[pass-a]` — **verified**

`config/swatter.example.conf` has no `REPEAT_ENABLE` in its escalation block, and
house style for dangerous booleans is `:-false` (`SWARM_ENABLE`,
`ABUSEIPDB_REPORT`, `ASN_SIGNAL_ENABLE`). A single future `:-false` read site
silently reintroduces the v1 M1 bug. Mandate one definition —
`: "${REPEAT_ENABLE:=true}"` in `lib/common.sh` — and have `test-config` print the
*effective* boolean after the same expansion the gate uses.

### M8 — CRITICAL-single inert during the widen is under-compensated
`[pass-b]` The three named compensating controls are a one-shot preview, a
tripwire that M2/B4 show is mis-aimed at gate D, and a freeze that does not
prevent a local customer outage.

## Minors

  "~1–2/day", contradicting the measured 5.37/16.
- **m3** `[pass-a]` The residue branch is `lib/score.sh:328-336`, not `:326`.
- **m4** `[pass-a]` The CRITICAL-single matcher is `reason LIKE
  '%critical_badpath%'` and never checks `reqs==1`, though the knob's name and
  docs say "single probe." Errs safe, but the language is wrong.
- **m5** `[pass-a]` Swarm consume issues temps only (`lib/swarm.sh:215-216`) —
  correctly *not* a bypass. Recorded as verified-clean.
- **m6** `[gap]` The tripwire's dedup key is `perm_rate.<hour>`
  (`lib/score.sh:124`), so it rotates hourly and `ALERT_REPEAT_TTL=21600` never
  suppresses across hours — a sustained over-threshold condition alarms every
  hour, and a real runaway is byte-identical to the noise.
- **m7** `[gap]` "Run one manual scan" is ambiguous, and the cautious-looking
  option is wrong: `--dry-run` sets report mode, which still advances ingest
  cursors, consuming log bytes without blocking. The live scan is correct; the
  spec must say why.
- **m8** `[pass-a]` `TODO.md` still says "just widen to 30".

## Disposition

Nothing declined. B1 and B4 invalidate two of the fixes this revision introduced,
so the design needs another pass before it becomes an implementation plan. B2,
B3, and B5 add scope to v2.11.0 (a pending-drain command, an installer flag, a
runbook) that the current document does not budget for.
