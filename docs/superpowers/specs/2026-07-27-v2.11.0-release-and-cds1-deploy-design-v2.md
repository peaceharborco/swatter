# Design v2 — v2.11.0 release and the cds1 deploy

**Written:** 2026-07-27, replacing
`2026-07-27-v2.11.0-release-and-cds1-deploy-design.md`, whose premise adversarial
review falsified. Read `…-design-review-grok.md` for what was wrong and why.

---

## 1. The actual situation

**The temp→perm recidivism ladder shipped in v1.0.0 and is running on cds1
today**, at `REPEAT_N=3` / `REPEAT_WINDOW_DAYS=7`, in enforce mode since
2026-06-12. This project's own earlier work measured it at **5.37 escalation
events/day, spiking to 16**. Permanent bans are being placed now, on the *least*
safe version of the ladder that exists.

The v1 design read the handoff's "nothing was deployed" as "the ladder is not
running." It refers to the unreleased *improvements*. That misreading inverted
the risk direction of the entire plan.

**Corrected framing: two of the unreleased changes reduce false permanent bans
on day one. The rest are inert, notify-only, operator-invoked tools, or
display — and one of them increases escalation in an edge case.**

| Unreleased change | Effect on live ban arithmetic |
|---|---|
| Unblock watermark (`6b2c033`) | Reduces false bans immediately: an operator's false-positive correction is no longer silently undone |
| Perm-gate residue fix (§4.1) | Reduces false bans immediately: report-mode ghosts stop perm-banning on sight |
| CRITICAL-single bar (`d689160`) | **No effect on day one.** Inert until every in-window temp carries the `rule=` stamp — `swatter_store_temps_all_critical_single` requires `tot == crit` (`lib/store_sqlite.sh:281`), and pre-deploy temps carry no stamp, so the bar only comes alive after a full `REPEAT_WINDOW_DAYS` post-deploy (§6 gate C) |
| Perm-rate tripwire (`7ea76ea`) | **No effect on ban arithmetic.** Notify-only — it raises an alert; it never gates, blocks, or delays a ban |
| `escalate-preview` / `rollback-ladder` | **No effect on ban arithmetic.** Operator-invoked tools — visibility and bulk undo, neither automatic |
| `top`/metrics enforced-count fix | **No effect on ban arithmetic.** Display only — corrects what an operator sees, not what gets banned |
| Remaining knob validation (§4.2) | **Increases escalation** in one edge case: an empty `REPEAT_WINDOW_DAYS` used to read as a never-firing 0-day window (the stale comment this corrects, `lib/common.sh:357-359`); validation now rewrites it to `7`, which *arms* the ladder where it was previously inert |

**Therefore shipping sooner is still the safer act — but the case rests on two
changes, not seven.** The unblock watermark and the perm-gate residue fix each
reduce false permanent bans starting the day v2.11.0 deploys; every day cds1
stays on v2.10.0 is a day it bans repeat offenders without either fix. The rest
of the release — the raised CRITICAL-single bar, the tripwire, the
preview/rollback tooling, the display fix, and the knob validation — are
correct and worth shipping, but none of them carries the urgency argument: the
bar is inert on day one, the tripwire only alerts, the tools require an
operator to run them, the display fix changes nothing enforced, and the knob
fix nudges risk the other direction in its one edge case.

The genuine volume shock remains what `TODO.md` said all along: **widening the
window from 7 to 30 days.** That is the gated event.

## 2. Scope of v2.11.0

The merged escalation work and the `top`/metrics enforced-count fix, plus four
additions:

| Item | Why |
|---|---|
| `REPEAT_ENABLE` kill switch, **default on** | An abort lever the box has never had |
| Queued-perm gating | Without it the switch has a 24h bypass (§3.2) |
| Perm-gate residue fix | Live defect today; also resolves a display/engine contradiction |
| Remaining knob validation | Closes the last of a documented hazard class |
| `test-config` escalation dump | "Is the ladder armed?" is currently unanswerable |
| Tripwire calibration (§4.4) | The shipped default fires on cds1's *normal* behavior |

## 3. The kill switch

### 3.1 Placement and default

`lib/score.sh:607` is the only place a ladder perm is *chosen*:

```bash
if [[ "${REPEAT_ENABLE}" == "true" ]] && (( prior + 1 >= thresh )); then
```

**Default `true`.** Because the ladder is already live everywhere, default-off
would silently disable a protection every install has had since v1.0.0 — the
installer preserves an existing conf (`install/install.sh:238-242`) and will not
inject the key, so unset must mean "keep behaving as before." The switch exists
to *stop* the ladder in an incident, not to gate its introduction.

This inverts the house boolean convention's usual fail-safe direction, so it is
called out deliberately: here a typo'd value reads as `false` and **disarms**,
which is the safe direction for an abort lever.

### 3.2 The switch must also gate queued perms

`_swatter_retry_pending` (`lib/score.sh:377`) runs **first** in every scan
(called at `lib/score.sh:532`) and replays a stored intent through
`_swatter_apply_plane` (`lib/score.sh:484`) with no re-consultation of the
ladder or the switch. A ladder perm whose backend call failed while armed
lands up to `PENDING_RETRY_MAX_ATTEMPTS=12` attempts or
`PENDING_RETRY_MAX_AGE_HOURS=24` later (`lib/common.sh:135-136`) — **after**
the operator believes they disarmed.

The drain must therefore skip (and clear) queued rows whose `action='perm'` and
whose reason contains `recidivism=` when the switch is off. Without this the
switch is not an abort lever, it is a suggestion.

### 3.3 What "off" does not stop

Off gates ladder conversion only. These remain live and are correct to leave so —
they are independent features, not recidivism:

| Path | Location |
|---|---|
| Honeypot instant perm | `lib/score.sh:588` |
| Hard-intel dual-plane leg | `_swatter_maybe_dual_plane` (`lib/score.sh:358`) |
| Plane-upgrade (perm on the other plane) | `lib/score.sh:323` |
| Residue backfill (until §4 lands) | `lib/score.sh:341` |

**Operationally critical:** an operator watching the box with the switch off
**will still see permanent bans**, and must not read them as the switch having
failed. Ladder perms are the ones carrying `recidivism=` in the reason. This
belongs in the README and the runbook.

## 4. Fixes carried

### 4.1 Perm-gate residue

Require enforced ledger evidence at `lib/score.sh:336`
before the legacy backfill fires, matching `swatter_store_top_offenders` /
`swatter_store_counts` / `swatter_store_perm_ips_since`. Ban path: TDD, mutation
check, dedicated Grok pass. Sizing query and full rationale in v1 §4.1, which
review confirmed as sound.

### 4.2 Knob validation

Validate `SCORE_TEMP`, `MAX_BLOCKS_PER_RUN`, `WINDOW_SECONDS`, and
`MIN_REQS` using the existing `10#`-normalizing pattern. Also correct the stale
comment at `lib/common.sh:357-359`, which claims an empty `REPEAT_WINDOW_DAYS`
fail-safes to a 0-day window; validation (`lib/common.sh:378-384`) rewrites it
to 7 first, which arms.

### 4.3 `test-config` escalation dump

Report `REPEAT_ENABLE`, `REPEAT_N`,
`REPEAT_WINDOW_DAYS`, `REPEAT_N_CRITICAL_SINGLE`, `PERM_RATE_ALERT_PER_RUN`,
`PERM_RATE_ALERT_PER_DAY`, `SWARM_PUBLISH`, and `ABUSEIPDB_REPORT`. Every one of
these is a control the runbook needs to verify, and none is currently visible.

### 4.4 The perm-rate tripwire fires on normal cds1 behavior

`PERM_RATE_ALERT_PER_DAY` defaults to **15** (`lib/common.sh:80`). cds1's
measured escalation rate is **5.37/day, spiking to 16**
(`2026-07-24-recidivism-escalation-design.md:501`). A normal spike day therefore
already crosses the daily threshold — before any widening, and before honeypot
and hard-intel perms, which the tripwire also counts, are added on top.

This matters more than a stray alert. §7 makes a tripwire fire an abort trigger,
so an ordinary busy day would trip a spurious abort; and an alarm that cries wolf
during the soak is an alarm nobody trusts during the widening, which is the one
moment it exists for.

**The defaults are a placeholder, not a calibration.** They cannot be right for
every host — perm volume is a property of the traffic a box receives. The fix is
threefold:

1. **Ship the defaults unchanged.** 5/15 is reasonable for a small new install,
   and raising it globally would blunt the alarm for hosts where it is correct.
2. **Document loudly** — in the conf example, the README, and the `test-config`
   dump — that these must be calibrated against the host's measured rate, and
   that an uncalibrated tripwire produces alert fatigue rather than safety.
3. **Set cds1's values from measurement, not guesswork** (§6, gates B and C).

## 5. Release mechanics

Unchanged from v1 §5, which review confirmed. `make release V=2.11.0` after
finalizing the CHANGELOG and bumping `SWATTER_VERSION`; the script enforces clean
tree, `main`, in-sync, tag-free, suite-green, and version-matches.

## 6. The gates

### Gate A — build and release
Local only. Ends at a published `v2.11.0`. Grok review before the tag, mandatory
for the residue fix and the queued-perm gating.

### Gate B — capture the baseline, then deploy
**Checkpoint: confirm before touching the box.**

1. **Capture first, infer nothing.** Record `swatter version`, the enforced perm
   count, a sample of perm reasons (to separate ladder from honeypot/hard-intel),
   the §4 residue sizing query, and the live state of `SWARM_PUBLISH` and
   `ABUSEIPDB_REPORT`. The v1 design assumed cds1's state; that assumption is
   what produced a falsified premise.
2. **Deploy under a maintenance hold.** `install/install.sh` has no lock and no
   cron pause, so a scan starting mid-copy can source a mixed tree. Pause
   `/etc/cron.d/swatter`, install, `test-config`, run one manual scan, re-enable.
3. **Freeze publication now, not at gate D.** Set `SWARM_PUBLISH=false` and
   `ABUSEIPDB_REPORT=false` before re-enabling cron. Perms flow from the deploy
   onward, not from the widen — a false ladder perm minted during gate C's
   7-day soak is exactly as irretractable as one minted after gate D's widen,
   so waiting until gate D to freeze leaves the soak period unprotected.
   **This is a deferral, not a suppression:** `swatter_swarm_publish`
   (`lib/swarm.sh:61`) returns before reading or advancing its cursor file
   while `SWARM_PUBLISH` is `false`, so every confirmed perm placed during the
   freeze accumulates unpublished rather than being dropped. Restoring
   `SWARM_PUBLISH=true` later therefore publishes the *entire accumulated
   backlog* in one batch, not just what changed since — treat that restore as
   a reviewed step (audit what's queued first), never a blind flip once a
   calendar deadline passes (§6 gate D step 6).
4. **Set a provisional tripwire band before re-enabling cron** (§4.4). The
   shipped 15/day sits *below* cds1's known spike of 16, so leaving it would
   guarantee a false abort in the first days. Set a provisional
   `PERM_RATE_ALERT_PER_DAY` with clear headroom over the known spike, and record
   it as provisional — the real number comes from gate C. Do not skip this on the
   grounds that the tripwire is "just an alert": §7 makes it an abort trigger.
5. **The ladder stays ON.** This is not a no-op deploy — it changes ban
   arithmetic in the safer direction, which is the point. Expected deltas, not
   "no change": fewer premature perms from the watermark, and the residue fix.

### Gate C — soak, and let the new bar come alive
**~7 days, no config changes.**

The CRITICAL-single bar is inert until every in-window temp carries a `rule=`
stamp, because `swatter_store_temps_all_critical_single` requires `tot == crit`
(`lib/store_sqlite.sh:281`) and that stamp is added by the unreleased
`lib/score.sh:570`. Pre-deploy temps have none, so the bar sits inert — degrading
toward the *lower* threshold — until the whole window is post-deploy.

Soaking one full `REPEAT_WINDOW_DAYS` is what brings the safer bar live.

**The soak's other job is to produce the tripwire's real numbers** (§4.4). Over
the 7 days, record the per-day perm count and the per-run maximum — from the
ledger, which does not rotate, not from `decisions.jsonl`, which does. Then set
`PERM_RATE_ALERT_PER_DAY` and `PERM_RATE_ALERT_PER_RUN` at a defensible multiple
of the observed ceiling rather than a guess, and write the observed band into the
runbook so the abort rule in §7 has something concrete to compare against.

Note the soak measures the rate at a **7-day** window. Widening to 30 raises it
by construction, so the band set here is the baseline for detecting a *runaway*
during gate D, not a prediction of gate D's steady state.

### Gate D — preview at 30, review, then widen
**Checkpoint: the candidate list is reported for decision before anything flips.**

In order:

1. Populate `monitoring.cidr` — still empty, while `allow.cidr` holds three
   documented customer false positives.
2. `swatter escalate-preview --window 30` — **regenerate, never review a saved
   list.** Previewing at 30 is mandatory and non-substitutable: a clean list at 7
   says nothing about who appears when the window triples. This is the gate the
   handoff exists to enforce.
3. Human review: ASN, PTR, customer mapping, plane. Anything resembling
   NAT/CGNAT, mobile carrier, VPN exit, crawler, or customer is allowlisted
   **before** the flip.
4. Confirm the publication freeze from gate B is still active
   (`SWARM_PUBLISH=false` and `ABUSEIPDB_REPORT=false`) — it was set at deploy,
   not here, so there is nothing to change at this step. Both are
   irretractable outbound planes; v1 froze only the first, and froze it here
   rather than at deploy.
5. Set `REPEAT_WINDOW_DAYS=30`.
6. Watch the first 48h after the widen — this establishes gate D's own rate
   baseline (§7), which is what abort is judged against, not the gate C band.
   Then watch the first nightly digest. After 14 clean days post-widen, review
   what accumulated during the freeze (§6 gate B) before restoring
   `SWARM_PUBLISH` and `ABUSEIPDB_REPORT` — restoring publishes the whole
   backlog at once, so the review is the point, not a formality.

**Accepted risk at this gate:** widening to 30 pulls pre-deploy temps back into
the window, so `tot == crit` fails again and the CRITICAL-single bar goes inert
for a further 30 days. Waiting 30 days post-deploy to avoid this is judged too
long; the compensating controls are the preview review, the tripwire, and the
publication freeze.

## 7. Abort

**Trigger:** a **rate-of-change breach against gate D's own first-48h
baseline** (below), any customer-reported outage, or any perm whose candidate
was not on the reviewed list.

**Why not the gate C band.** Gate C's band is measured at a 7-day
(`REPEAT_WINDOW_DAYS`) window. Gate D widens that same window to 30 — more
than 4x wider — so the volume of temps eligible to convert to perms rises *by
construction* the moment the window flips, independent of any actual runaway.
Judging gate D against the gate C band guarantees one of two bad outcomes: a
tight band false-aborts on ordinary post-widen volume, or a band loosened to
avoid that stops catching a real runaway — silently, which is worse. Neither
serves the one alarm gate D exists for.

**The gate D band instead.** Treat the first 48h after the widen (§6 gate D
step 6) as gate D's own local baseline: record the per-run and per-day perm
peak observed in that window. From day 3 onward, the trigger is a
rate-of-change breach off *that* baseline — not off the gate C number. Set the
specific multiple from the observed 48h peak and write it into the runbook
once gate D data exists; do not guess it here, for the same reason gate C's
band is set from measurement rather than a default (§6 gate C).

The qualifier is still load-bearing. "Any tripwire fire" was the v1 rule, and
against the shipped default it would abort on an ordinary spike day (§4.4) —
teaching the operator to discount the one alarm that matters during the
widening. A fire inside the established band is a signal to look, not to
abort.

**Sequence — all three steps, in order:**

1. `REPEAT_ENABLE=false`.
2. **Drain queued ladder perms** from `pending_blocks` (§3.2). Skipping this
   leaves up to 24h of perms in flight.
3. `swatter rollback-ladder --since <timestamp recorded BEFORE the change>` —
   `swatter_ladder_perms_since`'s selector is strict `>` (`lib/store_sqlite.sh:227`),
   so a value noted after the fact loses everything in between.

**Known limits of the undo, all verified:**

- **It cannot see historical ladder perms.** The selector requires
  `recidivism=` in the reason, and that stamp is unreleased — so every ladder
  perm placed on cds1 before this deploy is invisible to it. Months of them, at
  ~5/day.
- **It can fail closed.** `cmd_rollback_ladder` (`bin/swatter:528`) waits 120s
  for the state lock (`bin/swatter:559`) and dies if it cannot get it; a long
  scan plus swarm publish can exceed that.
  Confirm the reported counts rather than assuming success.
- **A partial per-IP failure still clears the ledger row** while the firewall may
  hold — the customer stays offline. Non-zero `partial` in the summary demands
  manual follow-up.
- **Config revert is not a revert.** Lowering the window or disabling the switch
  lifts nothing already placed.

## 8. Testing

- **Kill switch:** no ladder perm when off at a state that would otherwise perm;
  TTL laddering still escalates; default is on; **a queued `recidivism=` perm is
  not applied while off**; `escalate-preview` and `rollback-ladder` still work.
- **Residue fix:** residue flag with no enforced perm does not backfill; a real
  legacy import still does; an enforced perm still noops.
- **Knob validation:** empty, non-numeric, and zero-padded input for each of the
  four.
- **Mutation-check every load-bearing predicate.** Four review rounds on the
  escalation work found defects a green suite had passed.
