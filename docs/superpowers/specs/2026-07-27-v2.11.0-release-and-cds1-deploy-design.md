# Design — v2.11.0 release and the cds1 deploy

**Written:** 2026-07-27. Supersedes the sequencing assumed by
`2026-07-24-recidivism-escalation-handoff.md`, which is otherwise still accurate.

---

## 1. The finding that reordered this work

The handoff and `TODO.md` both frame the remaining work as *"`REPEAT_WINDOW_DAYS`
is still 7 everywhere — widening to 30 is the change."* That framing is wrong in
a way that matters: **the recidivism ladder is not running on cds1 at 7 days. It
is not running at all**, because the code has never been deployed. The handoff
says as much — "nothing was deployed" — but the widening language reads as though
7 is live, and a future reader would plan around the wrong risk.

The consequence: **the deploy, not the widening, is the moment repeat temps start
becoming never-expiring perms.** Every precondition written for Phase 4 —
populate `monitoring.cidr`, review the candidate list, freeze `SWARM_PUBLISH` —
logically attaches to the deploy.

Two facts sharpen it further:

1. **There is no kill switch.** `REPEAT_N=3` and `REPEAT_WINDOW_DAYS=7` are
   hardcoded defaults (`lib/common.sh:102,108`) with no enable flag. Neither can
   be neutralised by configuration: validation accepts `REPEAT_N` 1–20 and
   `REPEAT_WINDOW_DAYS` 1–90, and anything outside those ranges — including `0`
   — is rejected with a warning and **falls back to the default**, i.e. silently
   arms the ladder. The only "off" today is "do not deploy"; the only undo is
   `rollback-ladder`, which runs after bans are already placed.
2. **cds1 has six weeks of enforced temp history** (enforce since 2026-06-12).
   Any IP already holding `REPEAT_N - 1` enforced temps inside the trailing
   window perms on its next offense — potentially minutes after the deploy.

## 2. Scope of v2.11.0

28 commits since `v2.10.0` at time of writing, features included, so a minor
bump — the count grows as the three additions below land. The release
carries the merged recidivism escalation work and the `top`/metrics enforced-count
fix, plus three additions decided here:

| Item | Why it is in this release |
|---|---|
| `REPEAT_ENABLE` kill switch | Makes the deploy separable from the behavior change |
| Perm-gate residue fix | Live on cds1 today; also removes a display/engine contradiction |
| Remaining knob validation | Closes the last of a documented hazard class |

## 3. The kill switch

### Placement

`lib/score.sh:557` is the only place a ladder perm is chosen:

```bash
if (( prior + 1 >= thresh )); then                                       # today
if [[ "${REPEAT_ENABLE}" == "true" ]] && (( prior + 1 >= thresh )); then  # proposed
```

When disabled, control falls through to the existing `else` branch —
`action="temp"` with `_swatter_pick_ttl`. That is the pre-2.11.0 path unchanged.

### What "off" means, precisely

Off gates **only the temp→perm conversion**. It deliberately does not touch:

- **`TTL_LADDER` / `PERSIST_N`** — escalating temp *durations* predate this work
  and remain active. "Off" means "today's behavior," not "less than today's."
- **`escalate-preview`** — must work while disarmed; previewing before arming is
  the entire point of gate C.
- **`rollback-ladder`** — an undo tool must not depend on the feature being on.
- **The perm-rate tripwire** — harmless at zero ladder perms, and still correct
  for perms from other paths (honeypot, hard intel).

### Default and surface

Default `false` in `lib/common.sh`, following the house boolean convention —
`[[ "${REPEAT_ENABLE:-false}" == "true" ]]`, as used by `SWARM_PUBLISH` and
`DUAL_PLANE_HARD_INTEL`. That convention is inherently fail-safe here: any value
that is not exactly `true` reads as off, so a typo disarms rather than arms. This
is the opposite of the numeric knobs, where an invalid value falls back to a
default that arms — which is precisely how `REPEAT_WINDOW_DAYS=0` fails today.

Documented in the conf example and README. `swatter test-config` gains a line
reporting its state, so "is the ladder armed?" is answerable without reading
config by hand.

Default-off is chosen over default-on because Swatter is public: an install
upgrading to v2.11.0 must not begin issuing permanent bans because of a version
bump. Arming is always an explicit act.

## 4. The two fixes

### 4.1 Perm-gate residue (ban path — requires review)

`lib/score.sh:326` is reached only when an IP has no `plane_blocks` row on either
plane. There it consults the global `offenders.perm` flag and, if set, backfills
an immediate permanent ban and returns 0 — so the caller **skips the ladder
entirely**. The branch exists for legitimate legacy imports.

The flag carries the same non-retroactive residue as `temp_count`: before
`15aad86`, a *dry-run* perm set it. On any host that ran report mode before
enforce — cds1 did — a report-mode-only IP can therefore be permanently banned on
sight, bypassing the ladder, the CRITICAL-single gate, and recidivism accounting.
This is current production behavior, not something this release introduces.

The `top`/metrics fix in `034726a` makes it worse in one specific way: `top` now
renders `PERM=0` for exactly these IPs while the engine still acts on the flag.
Display and behavior contradict each other until this is fixed.

**Fix:** require enforced evidence in the ledger before the backfill fires — the
same conjunct now used by `swatter_store_top_offenders` and
`swatter_store_counts`, and already the established idiom in
`swatter_store_perm_ips_since`. Legitimate `import-bans` entries are unaffected
because they write a real action row.

**Sizing query** (read-only, safe on a live host):

```sql
SELECT COUNT(*) FROM offenders o
 WHERE o.perm=1
   AND NOT EXISTS (SELECT 1 FROM actions p
                    WHERE p.ip=o.ip AND p.action='perm' AND p.dry_run=0);
```

Run at gate B. Zero means the concern is theoretical on this box; non-zero is the
count of IPs pre-loaded to perm on sight.

### 4.2 Remaining knob validation

Apply the existing `10#`-normalizing validation to `SCORE_TEMP`,
`MAX_BLOCKS_PER_RUN`, `WINDOW_SECONDS`, `MIN_REQS`. Under `set -u` a non-numeric
value can exit the shell mid-scan. Mechanical; the pattern is already in place for
the escalation and tripwire knobs.

## 5. Release mechanics

`install/release.sh` (via `make release V=2.11.0`) performs: verify → tag →
dual-push → GitHub Release → GitLab Release. It **refuses** unless the working
tree is clean, HEAD is on `main` and in sync with `origin/main`, the target tag
does not exist, the full suite passes, and `SWATTER_VERSION` in `bin/swatter`
already equals the target. So the ordered ritual is:

1. Land the three code changes (each TDD'd, suite green).
2. Grok review — mandatory for 4.1, which is a ban path.
3. Finalize `CHANGELOG.md`: rename `[Unreleased]` to `[2.11.0] - 2026-07-27`.
4. Bump `SWATTER_VERSION` to `2.11.0` in `bin/swatter`, commit.
5. `make release V=2.11.0 DRY=--dry-run`, read the output, then run it for real.

## 6. The four gates

### Gate A — build and release
Local only. Nothing reaches cds1. Ends at a published `v2.11.0`.

### Gate B — deploy with the ladder off
`./install/install.sh remote root@cds1`, with `REPEAT_ENABLE=false` in
`/etc/swatter/swatter.conf`. **Checkpoint: confirm before running.**

Expected: no behavior change. Verify with `swatter test-config` (reports the
switch state), confirm the `*/5` cron is healthy, and run the §4.1 sizing query.
The one write this performs on its own is a one-time build of the new
`ix_actions_enforced` index at first store init — cheap at this table size.

Post-deploy, `swatter top` finally reports enforced-only numbers, which is what
makes gate C's review trustworthy.

### Gate C — preconditions, preview, then arm at 7 days
In order, and the order matters:

1. Populate `monitoring.cidr` — it is empty, while `allow.cidr` holds three
   documented customer false positives from a single day. With it empty the
   allowlist is the only thing between a legitimate NAT/office/VPN/webhook IP and
   a permanent ban.
2. `swatter escalate-preview --window 7 > /root/escalate-7d.tsv`. Read-only, safe
   mid-scan. **Regenerate it — never review a saved list** (the pre-2026-07-24
   tool under-reported by one offense).
3. Human review: ASN, PTR, customer mapping, DIRECT vs CF plane. Anything
   resembling NAT/CGNAT, mobile carrier, VPN exit, crawler, or customer goes into
   the allowlist **before** arming. **Checkpoint: the candidate list is reported
   for decision before anything is armed.**
4. `SWARM_PUBLISH=false` for 14 days — the hub has host-wide purge only with a
   7-day TTL, so a false ladder-perm cannot be retracted per-IP once published.
5. Set `REPEAT_ENABLE=true`. This is the moment the behavior changes.

**Timing note — space gate B and gate C by ~7 days if practical.** The
CRITICAL-single gate (the *higher*, safer bar of 4) is inert for the first
`REPEAT_WINDOW_DAYS` after deployment because pre-upgrade temps carry no `rule=`
in their reason, so the ladder degrades toward *more* banning during that window.
Temps recorded after gate B do carry `rule=`. Waiting therefore heals the
inertness before the ladder is ever armed — an emergent benefit of splitting
deploy from arm, and the single strongest argument for not collapsing these gates.

### Gate D — widen to 30 days
Only after gate C is clean for 48h **and** the first nightly digest reads sane.
Set `REPEAT_WINDOW_DAYS=30`. **Checkpoint: confirm before flipping.** Then watch
again; after 14 clean days restore `SWARM_PUBLISH=true`.

## 7. Abort criteria and rollback

**Abort on:** any perm-rate tripwire fire (5/run or 15/day, against an expected
1–2/day net-new), any customer-reported outage, or any perm whose candidate was
not on the reviewed list.

**Abort action, in order:** set `REPEAT_ENABLE=false` (instant; stops new ladder
perms), then `swatter rollback-ladder --since <arm-timestamp>`, then diagnose
before re-arming.

**Two things rollback does not undo:**
- **Reverting config is not a revert.** Lowering `REPEAT_WINDOW_DAYS` or
  disabling the switch does not lift bans already placed; `offenders.perm` is
  sticky. Only `rollback-ladder` lifts them.
- **Off-box propagation.** The swarm hub has host-wide purge only with a 7-day
  TTL, and AbuseIPDB reports cannot be retracted per-IP. Hence the publication
  freeze in gate C.

## 8. Testing strategy

- **Kill switch:** the ladder does not perm when disabled at a state that would
  otherwise perm; TTL laddering still escalates when disabled; `escalate-preview`
  and `rollback-ladder` still function when disabled; default is off; an invalid
  value fails safe to off (not to on).
- **Perm-gate residue:** a residue flag with no enforced perm action does not
  backfill; a real legacy import still does; an enforced perm still noops.
- **Knob validation:** each of the four knobs falls back with a warning on empty,
  non-numeric, and zero-padded input.
- **Mutation-check every load-bearing predicate.** Four review rounds on the
  escalation work found defects the suite passed, and the end-to-end ladder test
  was only trusted after two mutations of its key lines were shown to fail it.
  Treat a green suite as necessary and not sufficient in this area.

## 9. Residual risks this design does not remove

- **The CRITICAL-single inertness window** is mitigated by spacing gates B and C,
  not eliminated. If they are collapsed, the safer bar is inert when it is most
  needed.
- **Partial-write skew.** `swatter_store_record` writes the action row and the
  offender row in two separate statements. A partial write (action lost, rollup
  kept) makes the enforced-only reads under-report. Rare and logged loudly, but
  under-reporting is the worse direction; noted so it is not rediscovered as a
  new bug.
- **`swatter allow` does not reset the ladder** — only `swatter unblock` does.
  This is the correct operator path for a false positive and is easy to get wrong.
- **Report-mode chronicity.** Since `034726a`, `OFFN` counts enforced actions
  only, so a report-mode week no longer distinguishes an IP seen once from one
  seen forty times. `swatter why <ip>` carries that history.

## 10. Out of scope

App-signal ingest (Path A) stays sequenced after this work, so a perm-volume
change has a clean baseline to be attributed against. No changes to the swarm hub,
the origin lock, or Cloudflare zone state — the last of which belongs in
`terminal-scripts` regardless.
